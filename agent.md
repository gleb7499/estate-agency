# agent.md — Источник истины для фронтенд‑агента

**Назначение:**
Этот документ — единый, авторитетный источник правил и практик для разработки одностраничной вёрстки (HTML/CSS/JS) под текущий проект (чат‑интерфейс поддержки). Нейросеть и любые автоматизированные агенты обязаны ссылаться на него перед генерацией кода или инструкций. При появлении ТЗ (технического задания) новые секции и плейсхолдеры будут заполняться и версия документа обновится.

## 1. Краткий обзор проекта
- **Тип проекта:** одностраничная вёрстка (UI для поддержки/чата).  
- **Стек:** минимум — чистый HTML + CSS + JS. jQuery допускается только при явной потребности.  
- **Адаптивность:** не требуется (минимальная ширина 1280px).  
- **Цель:** сделать чистую, изолированную и легко интегрируемую вёрстку, которую можно передать разработчику/интегратору (в нашем случае — Илье), который внедрит файл(ы) в legacy‑проект через FTP/SFTP.

## 5. Рекомендации по стилю кода
### 5.1 Общие правила
- Всегда **оборачивать страницу в корневой контейнер** с уникальным классом, например:
  ```html
  <div class="my-page mp-root">
    <!-- контент -->
  </div>
  ```
- Префикс для классов: `mp-` (mp = my‑page). Примеры: `.mp-header`, `.mp-btn`, `.mp-dialog`.
- Избегать общих имён (`.container`, `.button`, `.header`) без префикса.

### 5.2 HTML
- Использовать семантические теги (`header`, `main`, `section`, `nav`, `footer`).  
- Минимально возможная вложенность.  
- Чёткие id только для точек интеграции, иначе — классы.

### 5.3 CSS
- **Изоляция:** все правила ограничивать в рамках `.mp-root` (или `.my-page`):
  ```css
  .mp-root .mp-header { /* ... */ }
  ```
- Допускается локальный reset внутри корня:
  ```css
  .mp-root * { box-sizing: border-box; margin: 0; padding: 0; }
  ```
  Но **не** применять глобальные ресеты к `body` или `html` — это может сломать хост‑сайт.
- Не радикально переопределять системные селекторы (например `a`, `button`, `input`) вне контекста `.mp-root`.
- Порядок в css: переменные, базовые утилиты, блоки (header/content/footer), компоненты, утилитарные классы.

### 5.4 JS
- **Предпочтение:** ES6 (модули, стрелочные функции, `const`/`let`). jQuery допускается, если проект требует совместимости с legacy кодом (но уточнить у интегратора).
- **Скоупинг:** всегда искать селекторы внутри `.mp-root`:
  ```js
  const root = document.querySelector('.mp-root');
  root.querySelectorAll('.mp-btn').forEach(...);
  ```
- Использовать IIFE / модульный паттерн, чтобы не загрязнять глобальный объект `window`.
- Не навешивать глобальные обработчики на `document`/`window`, если можно вешать внутри корня (исключение — действительно глобальные события).

### 5.5 Стандарты форматирования
- HTML: аккуратная структура, 2 пробела отступ.  
- CSS: 2 пробела, свойства в алфавитном или логическом порядке (обсудить в ТЗ).

## 6. Инструкции по тестированию (чеклист)
**Ручной чеклист перед сдачей:**
1. Открыть страницу через простой static server (см. команды выше).  
2. Проверить визуальные компоненты: заголовки, кнопки, поля ввода, отступы.  
3. Проверить интерактивность: клик по кнопкам, отправка формы, открытие модалок.  
4. Проверить корректность путей к картинкам/шрифтам (относительные).  
5. Проверить отображение в Chrome и Firefox (минимально).  
6. Проверить возможные конфликты со стилями хоста: вставить `.mp-root` внутрь тестовой страницы со «вредоносными» глобальными стилями и убедиться, что внешние стили не ломают ключовые элементы.  
7. В JS: убедиться, что ошибки в консоли отсутствуют.  

**Тесты на интеграцию (для Ильи/intergation dev):**
- Загрузить файлы на staging/тестовый поддомен или в подпапку реального сайта и проверить, не ломает ли это остальной сайт.  
- Прогнать smoke‑проверки: входы/клики/формы.

## 7. Соображения безопасности
- **NDA:** хранить и обмениваться конфиденциальной информацией в соответствии с подписанным NDA.  
- **Никогда** не коммитить в репозиторий секреты (пароли, ключи, .env).  
- **FTP vs SFTP:** FTP передаёт данные в открытом виде. При возможности рекомендовать SFTP/FTPS.  
- Перед загрузкой на живой сервер — обязательно **создать резервную копию** (backup) оригинальных файлов.  
- Скрипты должны избегать выполнения произвольного кода из ненадежных источников; валидация и санитизация данных — на бэкенде.  
- Для фронтенда: избегать внедрения inline‑скриптов, если это конфликтует с CSP на целевом сервере.

## 8. Дополнительные инструкции (коммиты, PR, баги, деплой)
### 8.1 Правила коммитов
- Формат коммита: `type(scope): краткое описание`  
  Примеры: `feat(layout): add chat list layout`, `fix(css): correct button padding`.
- Сообщение должно объяснять «почему», если это не тривиальная правка.

### 8.2 Pull Request (шаблон)
PR должен содержать:
- Краткое описание изменений.  
- Список файлов/директорий, которые изменились.  
- Как протестировать локально (шаги).  
- Скриншоты до/после (если применимо).  
- Чеклист: `[] Код работает локально`, `[] Нет ошибок в консоли`, `[] Стили изолированы`.

### 8.3 Issues / безопасность
- Вопросы безопасности помечать меткой `security`.  
- Немедленные проблемы (секьюрити) — сообщать контакту/владельцу (PLACEHOLDER: `[TBD: контакты]`).

### 8.4 Большие наборы данных
- Если проект потребует загрузки больших медиа/данных — вынести их в отдельный storage (PLACEHOLDER: `[TBD: облачное хранилище / CDN]`).

### 8.5 Этапы развертывания (шаблон)
1. Провести code review и тесты.  
2. Создать бэкап текущих файлов на сервере.  
3. Загрузить только изменённые файлы (diff) через SFTP/FTP.  
4. Очистить кеши (CDN, браузер).  
5. Прогнать smoke‑tests на проде.  
6. Роллбек план (как откатывать) — PLACEHOLDER: `[TBD: rollback instructions]`.

## 9. Интеграция через FTP — подробный чеклист для интегратора (Ильи)
1. **Бэкап** текущей папки/файлов на сервере (локальный архив с датой).  
2. **Проверить права** на папки/файлы (chmod/owner).  
3. Загрузить `index.html`, `css/style.css`, `js/script.js`, `assets/` в тестовую подпапку (например `/staging/mp-page/`).  
4. Открыть тестовую подпапку в браузере и проверить визуально.  
5. Перенести файлы в целевую директорию (если всё ок).  
6. Прогнать smoke‑тесты и проверить логи сервера на предмет ошибок.

> Совет: загружать сначала лишь `index.html` и css, проверить статичную версию, затем js, чтобы быстрее обнаружить конфликты стилей.
